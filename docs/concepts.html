model

Apple paths stay real.

Transparent mode mounts external APFS sparsebundles at the paths Apple tools already use. Shims are optional. The mounts are the storage mechanism.

Storage root

Every command accepts --root PATH, or reads MACOS_OFFLOAD_ROOT. Point it at a mounted external volume or another writable location you chose. 

/Volumes/YourExternalVolume/Xcode/

  XcodeDefaults/
    DerivedData.sparsebundle
    Archives.sparsebundle
  UserBackups/

Why APFS sparsebundles

Sparsebundles keep the heavy data off the internal disk while giving macOS a normal APFS filesystem at the mountpoint. They also give the tool something concrete to inspect with diskutil, mount, and hdiutil info.

Why not symlinks

CoreSimulator and simdiskimaged can reject symlinked mount parents. macos-offload treats a symlinked managed path as invalid. Replace it with a real directory before mounting.

Launchd responsibilities

One persistent user LaunchAgent subscribes to Disk Arbitration events and reconciles the user-owned mounts. CoreSimulator system paths remain internal. No root LaunchDaemon or root simctl process is part of the supported design.

xcodes compatibility

The xcodes profile keeps installed Xcode apps directly under the external Xcode root. It sets XCODES_DIRECTORY to that directory, then uses xcode-select as usual.

Shims are optional

Shims help with explicit argument routing, build products, archives, and TMPDIR. When APFS mount mode is active, default Apple tools can use the mounted paths without shims.
